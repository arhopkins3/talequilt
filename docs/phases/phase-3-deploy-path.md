# Phase 3: Deploy path

**Exit test:** a change reaches production only after Alex approves, and a failed smoke test rolls it back.

## Brief

### What this phase adds

The road from `main` to a running system, built so that the road itself is under the same controls as the code. Azure resources are declared in Bicep under `infra/` and created by the pipeline, never by hand in the portal. GitHub Actions signs in to Azure with OpenID Connect, so no cloud credential is stored anywhere. Every merge to `main` deploys to a staging environment and runs end-to-end tests, a dynamic security scan and accessibility checks against it. Promotion to production waits for Alex's approval on a GitHub environment (gate G4), then runs smoke tests and rolls back automatically if they fail. Runtime secrets live in Key Vault and are read through managed identity. The Checkov scan built in Phase 2 starts doing real work on the Bicep, and the SBOM gets a release to ride on.

### The problem it solves

Phases 1 and 2 proved that nothing broken, vulnerable or leaked can reach `main`. Nothing yet proves that what reaches `main` can run, or that production changes only when a named human says so. Deployment is where most real incidents happen: a hand-edited setting that differs between environments, a credential in a pipeline variable that leaks, a release nobody can roll back at two in the morning. Phase 3 makes deployment a reviewed, repeatable, reversible act with an audit trail: the Bicep diff is in the pull request, the deploy is a workflow run, the approval is recorded on the environment, and the rollback is automatic.

### Terms, defined once

- **Bicep:** Azure's declarative language for infrastructure. A template describes the resources wanted; a deployment makes reality match. `what-if` shows the difference before applying it, which is the infrastructure equivalent of a diff.
- **OpenID Connect (OIDC) federation:** GitHub Actions presents a short-lived signed token saying "this is run N of workflow W on branch B in repository R", and Azure is configured to trust that exact claim for one identity. No secret is created, stored or rotated.
- **Managed identity:** an identity Azure gives to a resource (a container app, a workflow's federated identity) so it can call other Azure services without a password. Key Vault grants it read on the secrets it needs.
- **Container Apps:** Azure's serverless container host. Each deploy creates a new *revision*; traffic can be split or shifted between revisions, which is what makes rollback a one-line call.
- **GitHub environment:** a named deployment target with its own secrets, variables and protection rules. A *required reviewer* on the `production` environment is what turns a workflow step into gate G4.
- **Smoke test:** a handful of requests against the deployed system that prove it is alive and wired correctly, run in the first minute after a deploy, as distinct from the full end-to-end suite run on staging.
- **DAST (dynamic application security testing):** scanning the running application rather than its source. OWASP ZAP's baseline scan requests pages and reports missing headers, insecure cookies and the like.

### Alternatives

ADR 0007 (hosting shape) is proposed and names the options with idle-cost estimates; this phase prices them from the calculator and accepts the ADR. The survey below carries the remaining decisions; each becomes an ADR or an amendment.

### At company scale

A platform team owns a landing zone (networking, policy, monitoring, identity) and product teams deploy into it from templates they do not edit. Infrastructure changes go through the same pull request gates as code, with policy-as-code (Azure Policy, Checkov or similar) blocking non-compliant resources before they exist. Environments are many (dev, test, staging, pre-production, production), approvals are tied to change tickets, and deployment windows and freeze periods are enforced by the pipeline. Rollback is a tested runbook, not a hope. Cost is tagged and charged back; a budget alert is a page, not an email.

## Decide

Settled in the Phase 3 survey on 13 October 2026 and recorded in ADR 0021. Seven of the eight were taken as recommended. On question 2 Alex first chose production only, to hold cost down until the app was established, then reversed on question 7 when asked where the end-to-end, security and accessibility tests would run before a change took traffic. The questions and options are kept below as the record of what was considered.

1. **Compute shape.** Confirm ADR 0007's first option: Container Apps (consumption) for the API and the worker, Static Web Apps for the React build, Azure SQL serverless with auto-pause, Storage for blobs and queues, Key Vault, Log Analytics. Recommendation: confirm, then price it; the alternatives are kept in the ADR.
2. **Environments.** (a) Staging and production, both from the same Bicep with a parameter file each, in two resource groups; (b) production only, with the end-to-end tests run against a temporary deployment. Recommendation: (a). The exit test needs somewhere for a bad deploy to fail before Alex sees it, and two environments from one template is the pattern worth learning.
3. **Public exposure before sign-in.** ADR 0008 forbids a public hostname for the API or the web app until sign-in exists in Phase 5. (a) Restrict the API's ingress to an IP allow-list and protect the web app's routes with Static Web Apps' built-in authentication (GitHub provider, invited users only), as a stopgap; (b) bring Google sign-in forward into this phase; (c) deploy only the API and worker, with internal ingress, and leave the web app undeployed until Phase 5. Recommendation: (a). It keeps the phase about deployment, satisfies ADR 0008's intent, and is removed in Phase 5. Changes to it are never classed as small.
4. **Pipeline identity.** (a) A user-assigned managed identity per environment with a federated credential for this repository and that environment, holding Contributor on its resource group only; (b) one app registration with a client secret in GitHub. Recommendation: (a). It is CLAUDE.md rule 8 made concrete, and the two identities mean the staging workflow cannot touch production.
5. **Database migrations.** (a) The API applies EF Core migrations at startup; (b) the pipeline runs a migration bundle against the environment's database before the new revision takes traffic. Recommendation: (b), with one rule that makes (b) safe: every migration must be compatible with the revision still serving, so a column or table is added in one release and only removed in a later one once nothing reads it (expand first, contract later). The migration runs while the old revision is live and a traffic shift does not undo it, so without that rule a rename or a drop would break both the running revision and the rollback. Database recovery is a separate path, point-in-time restore from Azure SQL's automatic backups, rehearsed in the drill and never implied by a traffic shift.
6. **Rollback.** (a) On a failed production smoke test, the workflow shifts traffic back to the previous Container Apps revision and marks the run failed; (b) redeploy the previous image. Recommendation: (a). Revisions make it seconds rather than minutes, and the previous revision is already warm. Rollback moves traffic only; it leaves the database as the migration left it, which is why decision 5 requires that migration to be compatible with the previous revision.
7. **Tests on staging.** Playwright end-to-end (the health and books pages), an OWASP ZAP baseline scan, and accessibility checks with axe through Playwright, all required before promotion is offered; production gets the smoke test only. Recommendation: all three on staging from the start, with the suites small and the thresholds explicit.
8. **Budget.** An Azure budget with alerts at £10 and £20 a month, staging scaled to zero between runs, SQL auto-pause on both environments. Recommendation: as stated; the price is in the accepted ADR 0007 and on the Console.

## Build

Four pull requests, each reviewable in one sitting.

1. **Infrastructure.** Bicep for one environment (parameterised), an `Infrastructure build` check that compiles and lints it with a pinned Bicep CLI, Checkov now scanning real files, and a documented one-time bootstrap script (resource groups, the two managed identities and their federated credentials) that Alex runs once from his own session, recorded in the ADR, because the pipeline cannot create the identity it signs in with. The `what-if` step moves to pull request 2, since it needs those identities to sign in with.
2. **Staging deploy.** In two parts. First, container images: the API and the worker are published by the .NET SDK's container support (no Dockerfile) to GitHub Container Registry, built on every pull request and pushed from `main` tagged with the commit, so the image deployed is exactly what `main` built. Also in the first part, the web app is made ready for Static Web Apps: the build takes the API's origin as `VITE_API_BASE_URL`, the API allows that origin and no other through a CORS policy read from configuration (set by the Bicep from the web app's hostname), and `staticwebapp.config.json` puts every route behind the `author` role that only an invited user holds, the ADR 0008 stopgap. Second, a `Deploy` workflow that runs when CI succeeds on `main`: publish the images for that commit, sign in with OIDC as the staging deploy identity, show the `what-if` plan, deploy the Bicep with the images already running, run the migration bundle as the SQL administrator (the deploy identity), grant the app identity and Alex their roles by Entra identifier, roll the new images out, wait for that new API revision to report healthy, build the web app against the API's hostname and upload it to Static Web Apps. Only a CI run for a push to this repository's `main` (or a manual run from `main`) triggers it. The `staging` environment exists with no protection rule.
3. **Verify and promote.** In two parts, so each is reviewable in one sitting. First (3a), the production path: the staging job becomes a reusable workflow (`deploy-environment.yml`) that `Deploy` calls once for `staging` and once for `production`, so what runs in production is the same steps that ran in staging with a different environment name. The `production` job carries the `production` GitHub environment, whose required reviewer is Alex, so it waits there for his approval (G4). After each rollout the workflow smoke-tests the API from outside: it adds an allow-list entry for the runner's address for the length of the job, expects `/api/health` to answer 200 Healthy, checks the web front door sends an anonymous visitor to GitHub sign-in, and removes the entry. If any step after the rollout fails, traffic shifts back to the revision that was serving before the run, both apps return to their previous images, the failed revision is deactivated, and the run stays red. Second (3b), the staging test suites: Playwright end-to-end and axe against a local production build of the web app pointed at the staging API, and an OWASP ZAP baseline against the staging API, all between the staging deploy and the production job, so a failure stops promotion being offered. The Console shows the two environments and the gate.
4. **Accept and price.** ADR 0007 accepted with calculator prices and the first month's actual bill when it exists, the budget alerts, the operating model's stage 5 and 6 rows marked enforced, and the learning log entry after the drill.

### Infrastructure scan findings and what was done with them

Checkov's first run on real Bicep (pull request 1) reported fourteen findings. Eight were fixed in the templates: database-level auditing, server and database security alert policies with email, geo-redundant storage. Six are suppressed in the Bicep with the reason beside each, all for one cause: private endpoints and default-deny network rules need a virtual network, and the consumption Container Apps plan has none. Key Vault (CKV_AZURE_109, 189), Storage (CKV_AZURE_35, 59) and SQL (CKV_AZURE_113) therefore stay reachable over their public endpoints with identity-only access, TLS 1.2 and auditing on, to be reviewed in Phase 5 when there is user data to protect. SQL zone redundancy (CKV_AZURE_229) is declined on cost for a single author. Two further suppressions (CKV_AZURE_26, 27 on the database) are false positives, since the alert policies they ask for exist as separately declared children. Two findings remain visible and are known false positives that Checkov will not suppress: CKV_AZURE_23 and CKV_AZURE_25 on the `existing` reference to the `master` database, which the template reads to route audit events and does not create.

### One-time settings (Alex applies)

**First staging run, 20 October 2026.** The first `Deploy` run on `main` published both images and then failed at the Azure sign-in with `AADSTS700213: No matching federated identity record found`. GitHub presents this repository's OpenID Connect subject in its immutable format, `repo:arhopkins3@687013/talequilt@1409238011:environment:staging`, the default for repositories created after 15 July 2026, while the bootstrap had registered the older name-only subject. The bootstrap now computes the immutable subject from GitHub's public API and updates the credential in place, so re-running `infra/bootstrap.sh staging` repairs it. A candidate for the debrief: the pipeline's one hand-made object was the one that drifted from its platform's current format, and the gate caught it before any resource was touched.

**Runs 2 to 7, 20 October to 24 November 2026.** Each later run failed one step further on, and each failure became a pull request: the Static Web Apps free-tier quota (three old sites deleted by hand), the worker's queue scale rule with no identity, four SQL security resources racing to write the same alert policy, a lock file left stale by a Dependabot merge, and in run 7 the SQL firewall refusing the GitHub runner, which came from an address outside Azure where the "allow Azure services" rule does not reach. The workflow now opens a firewall rule for the runner's address at the start of the database steps and removes it at the end of the job. Run 5 reached the health wait and the API revision never became healthy; the workflow now prints the revision's details and container logs when that happens, so the next run explains it.

**Build 3a, 24 November 2026.** The staging job was lifted into a reusable workflow unchanged and called twice. Three choices from the survey: the smoke test reaches the API through a per-run allow-list entry for the runner rather than a permanent one or a public endpoint, because the stopgap in ADR 0008 holds and an entry that lives for one job and is owned by the Bicep leaves nothing behind; the end-to-end tests in 3b run a local production build against the staging API, because the web app itself is behind invited-user sign-in that a test runner cannot complete; and the work is two pull requests, so the production path can be reviewed and approved on its own. The rollback shifts traffic first (seconds) and only then returns the apps to their previous images, so the template, the newest revision and the traffic agree again once it finishes; on a first deployment, with no previous revision, it does nothing.

**Run 15, 24 November 2026: the first run through G4.** The first run of the reusable workflow deployed staging as before and passed both new smoke tests, then waited at the production environment until Alex approved it. Production failed in its first step that touches Azure, the what-if, because the storage account name for `production` came out 25 characters and Azure allows 24; `staging` is two letters shorter and had never hit the limit. The name is now cut to 24 characters, which leaves staging's unchanged. Two things the run proved before failing: the gate held (the job did not start until the approval was recorded), and the what-if is where a bad template fails, before any resource exists.

**Run 16, 24 November 2026: the second run through G4.** Approved at 17:12, production passed the what-if and failed five minutes into the Bicep deploy, on the last module: the budget's start date was fixed in the template as `2026-10-01`, the month staging was first deployed, and Azure refuses to create a monthly budget whose start date is in an earlier month. Staging never saw it because its budget already existed. The start date is now the first of the current month, computed when the deployment starts, which is what the Azure Verified Module for budgets does. Everything before the budget was created, so the next run finds the production resources in place and finishes the rest. A note for the debrief: the what-if passed, because this rule is checked when the resource is written, not when the template is validated; the drill's "drift" step should include a date-dependent resource.

**Build 3b, 25 November 2026.** The staging test suites sit in a `Staging tests` job between the staging deploy and the production job, which now needs them. Playwright drives a local production build of the web app served by `vite preview`, whose `/api` proxy points at the staging API; the build is made without `VITE_API_BASE_URL`, so its calls stay same-origin and the API's CORS policy is not involved (the deploy's own smoke test covers the real cross-origin path). Three checks: the app reports the API healthy and lists books, a book can be added (one row per run, titled with the run id), and axe finds no serious or critical WCAG 2.1 AA violations. ZAP's API scan reads the API's OpenAPI document, now served in every environment behind the allow-list, and runs the passive and API-policy active rules against each route; `.zap/api-rules.tsv` says which findings fail the run (injection, code execution, disclosure, the security headers) and the rest are reported. The scan posts books to staging, which is what staging is for. The runner reaches the API through a per-run allow-list entry, as the smoke test does, and both reports are kept as artifacts. Alongside: the API now sends strict security headers on every answer and no `Server` header, with tests; the web app says "waking up" and retries for a minute instead of reporting the API unhealthy during a cold start, names the allow-list when it is refused, and shows a plain page to a signed-in visitor without the `author` role; and the comment that made the Static Web Apps CLI warn has left the config file. The first run after merge will show whether the ZAP policy needs tuning; a verdict changes only with a reason in the rules file.

**Run 18, 25 November 2026: the first production deploy.** Staging passed with its budget untouched, the production job waited at G4 from 10:59 until Alex approved it at 11:10, and production completed in six and a half minutes: the budget created, the database migrated, the identities granted, the images rolled out, the new API revision healthy in half a minute, both smoke tests passed, the web app uploaded and its front door locked. Build item 3a is complete: a change now reaches production only after Alex approves, which is half of the phase's exit test. The other half, a failed smoke test rolling back, is the drill's to prove. One loose end for 3b: the Static Web Apps CLI prints a schema warning about the `$comment` field in `staticwebapp.config.json` before deploying it anyway; the comment moves out of the file.

**Run 17, 25 November 2026: the budget fix broke staging.** The fix for run 16 set the budget's start date to the first of the current month on every deploy. Azure accepts that for a new budget and rejects it for an existing one: `Start date of budgets cannot be updated`. So staging, whose budget dates from October, failed in the Bicep deploy, and production, whose budget did not exist yet, never ran. The pull request had named that risk and shipped anyway; the rule now is that a change to a resource's identity-like property is tried on staging's what-if before it is merged, not after. The start date is now a parameter the workflow supplies: the existing budget's own date when there is one, otherwise the first of the current month, in the same step that keeps the running images. Both environments then deploy without touching a date Azure will not let change.

**Run 10, 24 November 2026: the first green deploy.** With the firewall rule in place the whole chain ran in about eleven minutes: images published, sign-in, what-if, Bicep, migrations, grants, rollout, the new API revision healthy in about a minute, web app built and uploaded. Runs 11 and 13, triggered by dependency merges the same afternoon, repeated it unchanged. Build item 2 is complete; the staging environment is live and reachable from the allow-listed address and by invited users.

## Break it: the drill

1. **Unapproved production deploy.** Merge a change and do nothing. Expected: staging deploys and passes; the production job waits on the `production` environment and nothing reaches it.
2. **Failed smoke test.** Merge a change whose health endpoint returns 500 behind a flag only production sets. Expected: staging passes, Alex approves, the smoke test fails, traffic shifts back to the previous revision, the run is red, and the site still works on the old revision. The change is then reverted by a pull request through the same gates, so `main` and production agree again.
3. **Incompatible migration.** A pull request whose migration drops a column the current revision still reads. Expected: review holds it on the compatibility rule from decision 5; it is closed unmerged. If a company needed proof rather than review, staging would show it: the old revision errors the moment the migration runs, before promotion is offered.
4. **Insecure infrastructure.** A pull request that sets a storage account to allow public blob access. Expected: Checkov fails the pull request naming the rule; `what-if` shows the change.
5. **Stored credential.** A pull request that adds a client secret to a workflow's environment block. Expected: push protection or the secret scan stops it, and the review notes that the deploy workflow has no secret to add.
6. **Drift.** Change a setting by hand in the portal, then redeploy. Expected: `what-if` reports the drift and the deploy puts it back.
7. **Clean up.** Steps 3, 4 and 5 are pull requests that never merge: close them. Steps 1 and 2 have to reach `main` for the deploy workflow to run, so step 1's change is harmless by design and step 2's is reverted by a pull request through the same gates. Step 6 leaves nothing behind. Production ends on the revision it started on, and `main` carries no deliberate fault.

## Carried in from Phase 2

- Public exposure is forbidden before sign-in (ADR 0008); decision 3 above is the stopgap.
- Checkov has run on an empty `infra/` since Phase 2 and reports without blocking; this phase decides whether `Infrastructure scan` becomes required.
- The SBOM is produced on every run but attached to nothing; this phase attaches it to the release that deploys.
- Dependabot now proposes Actions bumps for the deploy workflow too; the pin check applies to it like any other.
- The Pages workflow is the only deploy so far and already waits for CI; the application deploy follows the same rule.
